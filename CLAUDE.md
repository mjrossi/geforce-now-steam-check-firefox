# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

A Firefox MV3 extension that badges Steam store and wishlist pages with NVIDIA GeForce NOW availability.

## Commands

Tooling (node, just) is pinned in `mise.toml` — run `mise install` once, then `just install` (`npm ci`). `just` lists all recipes.

- `just check` — full local gate (matches CI): typecheck + test + lint. Run this before considering work done.
- `just typecheck` — **two** passes: `tsc --noEmit` (browser sources, `tsconfig.json`) and `tsc --noEmit -p tsconfig.node.json` (build script). Both must pass.
- `just test` / `just test-watch` — Vitest. Run one file: `npx vitest run tests/index-feed.test.ts`; one case: `npx vitest run -t "recycled"`.
- `just build` — `node build.mjs` (esbuild) → `dist/`.
- `just lint` — builds, then `web-ext lint` over `dist/`. Must stay 0 errors / 0 warnings.
- `just dev` — launches Firefox with the extension loaded (the only way to verify live-DOM behavior; an agent can't do this).
- `just package` / `just sign` — distributable zip / signed `.xpi` (signing needs `WEB_EXT_API_*`).

Tests that touch the DOM start with `// @vitest-environment jsdom`.

## Architecture

**Data flow:** content script (store/wishlist page) → `browser.runtime.sendMessage` → background service → cached index lookup → response → badge rendered into the page.

- **Background (`src/background/feed-service.ts`)** is the only network/state owner. It routes three message types (`shared/messages.ts` — `gfn-lookup` from content scripts, `gfn-status`/`gfn-refresh` from the popup) via an exhaustive switch. `gfn-status` must never trigger a fetch. Content scripts never fetch.
- **Messaging (`src/shared/send.ts`)** is how *every* context reaches the background, and it **never rejects**: `sendMessage` throws when there's no live receiver (the MV3 background is an event page, so startup and extension-update windows both hit this), and an unhandled rejection means *no badge at all* in a content script, or a popup stranded on placeholder text. It resolves to `undefined` instead; callers validate the reply with the guards in `shared/messages.ts` rather than casting it, since `sendMessage` also resolves `undefined` when a listener declines. `src/shared/lookup.ts` is the content scripts' wrapper over it, degrading to `{ok:false, reason:"network"}` → "couldn't check".
- **Feed cache (`src/feed/feed-cache.ts`)** is pure and dependency-injected (`LoadDeps`: `getCache`/`setCache`/`fetchFeed`/`now`/`ttlMs`). `loadIndex` returns fresh cache, else refetches+rebuilds (12h TTL). **Key invariant:** on fetch failure it serves stale cache if present, and only returns `{ok:false}` when there's no cache at all — so the UI shows "couldn't check", never a false "not supported". The real `LoadDeps` lives in `feed-service.ts`; tests inject fakes.
- **All loads go through `feed/load-coordinator.ts`.** `loadIndex` is stateless, so nothing stopped concurrent callers each driving a full paginated fetch — the ordinary case being a restored session where every Steam tab wakes at once on a stale cache. `createLoadCoordinator` shares one in-flight `load()` across concurrent callers (so they share its failure too) and serializes `forceLoad()` against it, so a manual refresh never runs a second full paginated fetch alongside a lookup-driven one. (Serialization used to be load-bearing for a second reason — making `refreshCatalog`'s before/after `fetchedAt` comparison trustworthy — which it never fully achieved; see `refresh.ts` below.) The shared slot is cleared inside the operation's `finally`, not by chaining onto the returned promise — a chained handler runs a microtask after the awaiting caller resumes, which let a load issued right after a failure be handed that same failure instead of retrying.
- **`feed/refresh.ts`** holds `readStatus` (cache-only, never fetches) and `refreshCatalog`. **Refresh success is `LoadResult.refetched`, never `LoadResult.ok`** — `loadIndex` reports `ok` when it falls back to a stale cache, which is right for a lookup but would tell the user a failed refresh worked. `refetched` is set only on the branch that actually wrote a new cache entry, so a failed *write* doesn't count either. This replaced a before/after `fetchedAt` comparison that had a hole in it: the "before" snapshot was necessarily taken before `forceLoad` could claim its place in the queue, so a lookup-driven fetch landing in between moved the timestamp and a failed refresh reported success. `tests/refresh.test.ts` pins both the stale-cache case and the concurrent-write case.
- **Index build (`src/feed/index-feed.ts`)** is pure: `GfnApp[]` → `Record<steamAppId, {rtx}>`. Keeps each game's `STEAM` variant; `rtx` comes from the per-game `RTX_ENABLED` capability flag.
- **`resolve-state.ts`** maps a lookup response to a `BadgeState` (`supported`/`not-supported`/`unknown`/`needs-permission`); **`badge/`** renders it (`gfn-link.ts`'s `resolveBannerLinks` decides which deep links a banner can offer). The two content scripts (`store.ts`, `wishlist.ts`) are thin glue: find anchors, message the background, paint.

**Not all stale answers are equally bad, and the code is deliberately asymmetric about it.** A frozen *wrong* answer — "Not on GeForce NOW" for a game that is on it — looks authoritative, and a user cannot tell it is wrong or guess that reloading would change it. That is worth engineering against, and three things do: the stale-cache-over-failure rule in `feed-cache.ts`, `isDefinitive` in `resolve-state.ts`, and `wishlist-memo.ts` memoizing *only* definitive states so `unknown`/`needs-permission` stay retryable. A frozen **"couldn't check"** is cheap by comparison: it says plainly that it does not know, and a reload fixes it.

`store.ts` therefore retries twice (2 s, 10 s) and then stops, covering the one case that needs it — a page opened while the MV3 event-page background is still waking. After that the banner stays "couldn't check" until reload, **by design**. It previously ran a five-step backoff plus `visibilitychange` and `window` `focus` revival, in a separate tested `store-controller.ts`; that was ~130 lines and a test file spent rescuing the cheap failure, and it misfired on the common case — `retryPending()` reset the attempt counter, so every window focus restarted the backoff and an actively used browser never exhausted it. Don't reintroduce it without a failure that actually costs the user something. `wishlist.ts` needs no equivalent: scrolling supplies a steady stream of retries for free.

**A new catalog heals open pages, via `shared/catalog-epoch.ts`.** The manifest carries no `tabs` permission and no steampowered.com host permission, so `tabs.query` returns a tab with no `url` — `popup.ts` therefore has **no** reload-the-active-tab path, and adding one back would not work. Instead `feed-service.ts`'s `setCache` writes `EPOCH_KEY` alongside the cache in one `storage.local.set`, and both content scripts subscribe with `onEpochChange`. This needs no permission a content script lacks and reaches *every* open Steam page, not just the active one. It is what makes the popup's "Refresh catalog" button actually repair the page it was pressed for. On an epoch change `store.ts` resets its retry counter and re-runs (unconditional — a *definitive* answer is exactly what a new catalog can invalidate) and `wishlist.ts` calls `memo.forgetAll()` then re-runs. Because definitive answers can now change, the DOM stamp is `stateStamp()` from `resolve-state.ts`, not `state.kind`: supported→supported with a different RTX flag or deep-link id renders differently and must repaint.

**There are two permissions, neither of them the gate the UI once claimed.** Getting this backwards cost a release's worth of wrong UX and a false claim in the AMO reviewer notes, so it is worth stating plainly:

- **`store.steampowered.com` (`STEAM_ORIGINS`) governs whether badges appear on their own.** It comes from `content_scripts[].matches`, *never* from `host_permissions` — it has never appeared there in this repo's history. Firefox MV3 lists it in `about:addons` → Permissions and in the toolbar icon's per-site menu, granted by default. Withdrawing it does **not** disable the add-on: Firefox switches to *click-to-run*, injecting the content scripts into the active tab when the user clicks the toolbar icon. `hasStandingSteamAccess()` sees only the standing grant, so it reads false while a click-granted content script is running perfectly well, and **no API distinguishes "only when clicked" from a hard block**. Two rules follow, both learned by shipping the mistake: word this state as click-to-run, never as broken; and remember that *opening the popup is itself the granting gesture*, so anything it renders describes the state one moment before the user's click changed it. This is what the `!` badge and the popup's status light report — "not automatic", not "broken". The popup offers **`requestSteamAccess()`** to leave the mode in one click; `STEAM_ORIGINS` is mirrored into `optional_host_permissions` solely to make that call legal, since `permissions.request` rejects origins the manifest doesn't mark requestable and a `content_scripts` match alone doesn't count. **That key is why `strict_min_version` is 128** — it is unsupported below it, and Firefox 128 is also where the per-site control that creates this state shipped, so the remedy exists on exactly the versions with the problem. A denied request falls back to naming the Add-ons Manager, which is the only point at which those instructions are worth the space.
- **`games.geforce.com` (`FEED_ORIGINS`) is insurance, not a gate.** It is declared in `host_permissions`, which Firefox MV3 does not grant on install (only `web-ext run` auto-grants), and `permissions.request` only works from a user gesture in an extension *page* — hence `popup/` and `onboarding/`. But **the catalog fetch succeeds without it**: `games.geforce.com/graphql` answers `access-control-allow-origin: *`, allows the `content-type` header, and `fetchFeed` sends `credentials: "omit"`, so the request clears ordinary CORS. Verified against the live endpoint. What the grant buys is independence from NVIDIA's CORS policy. **Never describe it as required** — not in the UI, not to AMO reviewers.

`shared/permission.ts` + `shared/feed-origin.ts` wrap both; `FEED_ORIGINS` must match `host_permissions` and `STEAM_ORIGINS` must match both `content_scripts[].matches` and `optional_host_permissions` — `tests/origins.test.ts` enforces all three against `src/manifest.json`, because drift here is silent (a green light on a browser where nothing can appear). `background/permission-gate.ts` drives the toolbar badge, opens onboarding once on install, and warms the cache on any grant.

**A failed fetch is reported as a failed fetch.** `feed-service.ts` still returns `reason: "permission"` when the feed grant happens to be missing, but only so the badge can *suggest* the grant — the copy says "couldn't check — the toolbar icon may help", never that permission is the cause. It previously asserted causation, which was backwards: since the fetch works ungranted, the usual reason for failing is the network, and offline users were being pointed at a button that could not help them. `tests/badge.test.ts` pins the wording.

**Data source (see README + `feed-service.ts` header):** NVIDIA's catalog GraphQL API, `POST https://games.geforce.com/graphql` (the source the GFN web app uses). The legacy static `gfnpc-*.json` feed is abandoned and returns false negatives — do not go back to it. The schema is reverse-engineered (introspection is disabled); `apps(...)` caps `first` at 1300, so the catalog is paginated on `pageInfo.endCursor`. That split follows the usual rule: `feed-service.ts`'s `fetchAppsPage` owns the request, and **`feed/fetch-catalog.ts`'s `fetchAllPages` owns the walk** — pure over an injected page fetcher, so `tests/fetch-catalog.test.ts` exercises cursor advance, both end-of-catalog signals (`hasNextPage:false` *and* a null `endCursor`, which the server can send independently), and the `MAX_PAGES` bound without a `browser` global. **A mid-walk failure must keep propagating**: returning what arrived so far would cache a partial catalog as if it were whole, and every missing game would badge a confident "Not on GeForce NOW". Steam app id is parsed from each variant's `storeUrl` (which carries a `?utm_source=` suffix — the `/\/app\/(\d+)/` regex handles it).

**DOM injection is a good citizen:** everything injected is namespaced `gfn-check-*` (CSS in `badge/badge.css.ts`, one `<style>` per document via `ensureStyles`). SVG/markup is built with `createElement`/`createElementNS`, never `innerHTML`, to keep `web-ext lint` clean and avoid host/asset permissions. This must coexist with extensions like Augmented Steam.

**Wishlist row derivation (`src/content/wishlist-rows.ts`)** is the riskiest area and is unit-tested in isolation. The modern wishlist is a virtualized React list with hashed class names: when the legacy `.wishlist_row` selector matches nothing, rows are derived by seeding from `/app/` links + `/apps/` capsule images and climbing to each game's single-app block, excluding Steam chrome (`#global_header`, `#footer`, `.footerv2`, `#responsive_page_menu`). Because rows are recycled, injected pill slots are stamped with **both** `data-gfn-app-id` and `data-gfn-state` and re-rendered on either mismatch — the state stamp is what lets a row painted "couldn't check" (lookup still pending) be replaced once it resolves, since the app id alone would match. `wishlist.ts` memoizes only *definitive* states per tab via `content/wishlist-memo.ts` (`createStateMemo`, one per tab, unit-tested); `unknown`/`needs-permission` stay retryable so badges self-heal without a reload, and `forgetAll()` drops the lot when a new catalog lands. `isDefinitive` and `stateStamp` live in `resolve-state.ts` and are the shared rules for both content scripts; the attribute the stamp is written to (`STATE_ATTR`) lives in `badge/badge.ts` with the rest of the injected-DOM contract. `paint`'s `stateOf` argument is deliberately required — defaulting it would quietly reduce the check to app-id-only matching, which is the frozen-placeholder bug it exists to prevent.

**Build:** `build.mjs` bundles five entry points (`background`, `store`, `wishlist`, `popup`, `onboarding`) as IIFE (classic scripts, not modules), copies `src/manifest.json`, `icons/`, and the popup/onboarding HTML into `dist/`. Adding a script means adding it both here and in the manifest.

## Conventions

- Keep the fetch/transform split: I/O lives in `feed-service.ts`; transforms (`buildIndex`, `resolve-state`, `wishlist-rows`) stay pure and importable so they're testable without mocking `browser`. Prefer adding a test next to the pure function over testing through the message layer.
- Selectors that depend on live Steam markup (store placement anchors `.apphub_HeaderStandardTop`/`.page_title_area`/`#game_area_purchase`, wishlist chrome exclusions) are the things most likely to break and need manual `just dev` verification — flag them when touched.
- `docs/pre-release-testing.md` is the manual plan for everything unit tests structurally can't reach, and is step 0 of the AMO checklist. Note `just dev` **auto-grants the host permission**, so the permission opt-in — the most load-bearing behaviour in the extension — is invisible in the mode you develop in; those tests need a real install (`about:debugging` → Load Temporary Add-on → `dist/manifest.json`). The `!` toolbar badge tells you which mode you're actually in. When you add behaviour that depends on a real browser event, a permission state, or `storage.onChanged` reaching content scripts, add it there.
